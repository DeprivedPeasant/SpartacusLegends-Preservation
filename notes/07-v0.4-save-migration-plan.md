# v0.4 native save migration plan

## Objective

Migrate established v0.3.x installations from the PINE-backed JSON roster and
campaign stores to the game's native UserStorage objects without losing or
silently replacing player progress.

The migration is a one-time, client-assisted conversion. The game client will
serialize the restored live state into its native formats; the server will not
attempt to fabricate complete native objects from partial legacy snapshots.

After migration, ordinary startup and persistence must use only the native
server path. PINE remains available solely for migration and explicit recovery.

## Data mapping

| Existing data | Native object | Expected size | Migration source |
| --- | --- | ---: | --- |
| `data/profile.json` plus RPCS3 `PRG-DATA` | `0x80000001` | 4664 (`0x1238`) | Local-profile fallback followed by a native client autosave |
| `data/campaign.json` | `0x80000002` | 6148 (`0x1804`) | Restore once through PINE, then accept the client's native upload |
| `data/roster.json` | `0x80000003` | 21444 (`0x53C4`) | Restore once through PINE, then accept the client's native upload |

`profile.json` remains active after migration because the emulated economy
service still uses it for server-side balances, purchases, and inventory. It
must be backed up but must not be archived out of the active `data` directory.

## Authority rules

1. A structurally valid native object is always authoritative.
2. Legacy JSON may restore an object only when the corresponding native object
   is absent.
3. A malformed or wrong-sized native object is a recovery condition, not an
   absent object. Migration must stop and preserve both copies rather than
   automatically replacing it from legacy data.
4. Migration acts independently per type. For example, an existing native
   roster must not be touched while a missing campaign object is migrated.
5. New installations with no legacy JSON never start PINE.
6. No legacy file is deleted. Any successful conversion retains a timestamped
   pre-migration backup.

## Migration state machine

### `not_needed`

There is no applicable legacy JSON, or every corresponding native object is
already valid. Start the native server normally without PINE.

### `pending`

At least one valid legacy object has no native counterpart.

- Create a timestamped backup containing the complete active `data` directory.
- Record the objects requiring migration.
- Start the PINE companion in migration-only mode.
- Protect pending type-2/type-3 destinations from client uploads until their
  legacy state has been restored. This prevents the fallback campaign or
  one-gladiator roster from becoming authoritative during a failed migration.

### `restored`

RPCS3 has reached the validated post-login state and the migration companion
has restored a pending legacy object into live memory.

- Allow uploads for that object.
- Do not poll or write continuing changes back into the legacy JSON store.
- Wait for the game to run its native autosave.

### `captured`

The HTTP service has atomically stored a client upload of the exact expected
size for the restored object.

- Record its size and SHA-256.
- Mark that object complete and prevent any further PINE restore for it.
- Continue waiting if another object is still pending.

### `complete`

All applicable objects have valid native files.

- Write `data/migration-v0.4.json` with the source files, backup path, native
  object sizes and hashes, timestamps, and final status.
- Stop the migration companion.
- Leave the original JSON files unchanged in the active folder until the
  release's retention policy is finalized; the timestamped backup is the
  guaranteed rollback copy.
- Every subsequent startup uses native persistence without PINE.

If RPCS3 or the server closes before completion, leave the state as pending and
resume safely on the next run.

## PINE migration behavior

Adapt the existing bridge into a restore-once mode with independent roster and
campaign switches.

- Connect while RPCS3 starts and retain the current build, game, pointer, and
  runtime guards.
- Wait for stable backend state 26.
- Load and validate only the missing object's legacy JSON.
- Preserve the existing schema-1/schema-2 Legend adoption checks.
- Restore each selected object once and signal the migration coordinator.
- Do not perform the bridge's normal continuous JSON capture loop.
- Do not overwrite an object whose native file became valid while waiting.

If a legacy Legend graph cannot be resolved safely, preserve the source and
report a blocked migration. Never substitute the current fallback roster.

## Protected upload behavior

The HTTP UserStorage handler needs migration-aware upload gating.

- Reject or defer type-2/type-3 PUTs while that type is `pending` and has not
  reached `restored`.
- Continue accepting type 1 because it is not restored by the bridge.
- After the restore signal, require the exact native size before replacing the
  destination atomically.
- Never replace a valid native file with an invalid-length upload.
- Log accepted, rejected, and deferred uploads with type, size, and migration
  state.

The rejected-before-restore response must cause a safe client retry. Confirm
that behavior in a controlled live test before release; if the client does not
retry safely, stage the body outside the authoritative user-content directory
instead and discard pre-restore fallback bodies.

## Startup and user experience

On an established v0.3.x installation, normal v0.4 startup should detect and
enable migration automatically. Users should not need to discover a command-line
flag.

The console should report clear milestones:

```text
Legacy v0.3 save detected; one-time native migration enabled.
Waiting for RPCS3 IPC on port 28012.
Legacy roster restored; waiting for native upload.
Native roster upload verified (21444 bytes).
Legacy campaign restored; waiting for native upload.
Native campaign upload verified (6148 bytes).
Native profile upload verified (4664 bytes).
Migration complete. PINE is no longer required.
```

Existing v0.3 installers enabled RPCS3 IPC, so most upgrades should work
without configuration changes. If IPC is unavailable, retain upload protection
and display exact instructions. Do not allow the session to silently establish
a fallback native roster over the legacy data.

## Implementation phases

### Phase 1: coordinator and validation

- Add a migration coordinator responsible for detection, per-object state,
  backups, native size validation, hashes, and the completion marker.
- Unit-test fresh installs, completed installs, partial migrations, malformed
  native files, and interrupted/resumed migrations.

### Phase 2: restore-once bridge

- Add independent roster/campaign selection to the existing bridge.
- Add callbacks or thread-safe events for successful restore.
- Disable continuous legacy capture in migration mode.
- Retain the explicit `--legacy-roster-bridge` recovery/debug behavior
  separately from automatic migration.

### Phase 3: HTTP integration

- Pass migration state into the OnlineConfig HTTP handler.
- Protect pending destinations and validate exact upload lengths.
- Mark objects captured only after atomic persistence succeeds.
- Add HTTP integration tests for protected, accepted, invalid, and resumed PUTs.

### Phase 4: launcher integration

- Detect migration before starting components.
- Start PINE only when at least one eligible object requires it.
- Present progress and actionable blocked-state messages.
- Stop the migration component after completion while leaving the native server
  running normally.

### Phase 5: controlled live upgrade

Use copies of a known v0.3 data directory and keep the original native objects
outside the test directory.

1. Start with valid `profile.json`, `roster.json`, and `campaign.json`, but no
   native user-content objects.
2. Start the server normally and confirm automatic migration mode.
3. Cold-boot RPCS3 and wait at the main menu/Ludus.
4. Confirm the legacy roster and campaign appear before uploads are accepted.
5. Wait for all three exact-size native objects.
6. Close RPCS3 and the server normally.
7. Disable IPC or run the next server session in native-only mode.
8. Cold-boot and verify profile values, complete roster/equipment, roster-slot
   capacity, campaign progress, and normal shop behavior.
9. Make another roster/campaign/profile change, cold-boot again, and confirm the
   new native state supersedes the legacy snapshots.

## Acceptance criteria

- A fresh installation never attempts a PINE connection.
- A completed migration never attempts a PINE connection.
- Existing valid native objects are never overwritten by legacy JSON.
- Pre-restore fallback uploads cannot replace a pending legacy roster or
  campaign.
- Interrupted migration resumes without deleting or weakening the rollback
  copy.
- Exact-size native objects for all three types survive two native-only cold
  boots.
- Schema-1/schema-2 Legend failures remain fail-closed and recoverable.
- The migration marker contains enough information to audit which data was
  converted and to locate the backup.
